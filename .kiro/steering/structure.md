# Project Structure

## Folder Layout (backend)
```
pyq-backend/
├── src/
│   ├── config/        → DB connection, env setup (e.g. db.ts)
│   ├── routes/        → API route definitions
│   ├── controllers/   → business logic for each route
│   ├── models/        → database queries
│   ├── middleware/    → auth checks, error handling
│   ├── types/         → TypeScript interfaces
│   └── server.ts      → entry point (Express app, middleware, listen)
├── dist/              → compiled output (generated by `tsc`, gitignored)
├── .env               → secrets (gitignored, never commit)
├── .env.example       → committed template of required env vars
├── docker-compose.yml → local PostgreSQL
├── package.json
└── tsconfig.json
```
Some `src/` subfolders (routes, controllers, models, middleware, types) are planned and may not exist yet — create them as features are added.

## Layered Architecture (separation of concerns)
Keep responsibilities in the right layer. A request should flow:

`routes → controllers → models → database`

- **routes/**: define HTTP endpoints and attach middleware; delegate to controllers. No business logic here.
- **controllers/**: request/response handling and business logic; call models for data. No raw SQL here.
- **models/**: encapsulate all SQL / DB access using the shared `pool`. Return plain data, not HTTP responses.
- **middleware/**: cross-cutting concerns (error handling, validation, auth for admin routes).
- **config/**: infrastructure setup (DB pool, env). Import the shared `pool` from `config/db.ts` — do not create new pools.
- **types/**: shared TypeScript interfaces (e.g. Category, Exam, Paper).

## Database Schema (planned)
Relational hierarchy: **Category → Exam → Paper**.
- `Category` (id, name, slug)
- `Exam` (id, category_id FK, name, slug)
- `Paper` (id, exam_id FK, year, shift, language, s3_key, file_size, download_count, uploaded_at)

## Conventions
- **URLs / slugs**: user-facing paths are slug-based and hierarchical (`/category/exam/year/shift`), never query-param based — this matters for SEO on the frontend, and the backend should expose slug-friendly data.
- **Files in S3**: store only the `s3_key` in Postgres; never store file bytes in the DB or route them through the backend.
- **New endpoints**: add a route, a controller, and (if it touches data) a model function — keep each layer thin and focused.
- **Naming**: use kebab-case for slugs, camelCase for TypeScript variables/functions, PascalCase for types/interfaces.
